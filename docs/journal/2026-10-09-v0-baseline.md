# 2026-10-09：v0 baseline、系统日志与失败诊断

## 版本与目标

当前已提交基线：`e84b9d6`（DABstep benchmark runner）。本篇对应其上的未提交日志改动，
不把旧评测冒充为日志版的新评测。原有 `docs/architecture.md` 工作区修改保留不动。
以后精确运行版本以 `logs/versions/<version_id>.json` 的源码指纹和配置为准。

这次用户希望建立可持续追踪的机器日志和文字日记，并解释初版为何表现差。
我补全观测能力、复查真实失败轨迹，但没有调整 tool schema、查询实现、prompt、路由
或 termination policy，也没有增加 memory、多轮状态或新工具。

## 当前 Agent 能做什么

已有 LangGraph 的 agent → tools → agent 循环，模型决定调用和结束；工具通过统一
Tool interface 访问只读 LocalWorkspace。支持 CSV/JSON/Markdown，五个工具为
list_workspace、inspect_file、read_file、search_workspace（BM25）和 query_data（DuckDB）。
CLI、Streamlit 聊天调试及 benchmark runner 均可使用；评测页面能展示结果和失败轨迹。
这已经证明工程链路可运行，但还不能称为可靠的数据分析 Agent。

## 这次改进了什么

以前 benchmark 有最终 JSONL，CLI 只打印，UI 历史只在 session；没有统一版本关联。
现在三个入口都有逐事件 JSONL，包括用户问题、guidelines、模型消息、工具参数/结果/错误、
耗时、用量、最终答案或异常。普通运行失败也保留过程，不再依赖成功返回后才保存。
新增 commit/源码指纹、依赖、模型、prompt/schema 配置快照，区分未提交版本。
会话、线程、任务、执行和轮次标识分开；benchmark 新增 execution_id 连接原结果与事件日志。
这些 ID 不引入任何对话记忆。API key 不写入配置，已加载的常见凭据值做过滤；日志仍可能
包含业务数据，默认不入 Git。详见 [日志说明](../logging.md)。

我建立了本目录和项目协作约定，后续实质改动由开发助手继续写日记；不是运行时自动生成。
旧 CLI/UI 内容不能追溯恢复，开发聊天也没有被自动全文归档。

## 失败分析：不只是模型问题

### 1. 数据查询层存在静默错误，优先级最高

task 1273 一条 UNION ALL 查询同时比较 credit_true、credit_true_or_null、all_globalcard。
旧轨迹返回后两组 n=0；但随后独立查询 credit_true_or_null 返回 n=144、avg_fee=
0.12013194444444449。这不是同一数据的合理差异。

本轮把原 arguments 原样交给现有 QueryDataTool，连续三次得到的三组 n 分别为：
`(0, 0, 257)`、`(0, 144, 257)`、`(123, 144, 0)`，均被工具标为 success。
预期三组应为 `(123, 144, 257)`。复现 SQL：

```sql
SELECT 'credit_true' AS scope, COUNT(*) AS n,
       AVG(fixed_amount + rate * 10.0 / 10000.0) AS avg_fee
FROM fees WHERE card_scheme = 'GlobalCard' AND is_credit = true
UNION ALL
SELECT 'credit_true_or_null', COUNT(*), AVG(fixed_amount + rate * 10.0 / 10000.0)
FROM fees WHERE card_scheme = 'GlobalCard' AND (is_credit = true OR is_credit IS NULL)
UNION ALL
SELECT 'all_globalcard', COUNT(*), AVG(fixed_amount + rate * 10.0 / 10000.0)
FROM fees WHERE card_scheme = 'GlobalCard'
```

实现位置：`QueryDataTool.execute`，`tools/implementations/query_data.py`，将 BytesIO
JSON relation 注册为 view。进一步只读诊断中，相同 BytesIO+view 查询三次仍出现空分支；
改为在临时内存连接中先 materialize 为 table 后，三次均得到正确三组。
这把问题定位到当前 buffer-backed view 重复扫描路径；具体 DuckDB 内部原因尚未确定。
简单无过滤 COUNT UNION 没复现，不能只用简单 SQL 测试宣布修好。

结论：工具层正确性缺陷已复现，会提供互相矛盾的“成功”证据。不能要求 prompt 纠正
工具静默返回的错误，也不能据此把 task 1273 全归责于模型。生产查询实现本轮未改。

### 2. Tool interface 不够易用，但不必立即推翻 abstraction

最集中的是 read_file：模型反复把 locator/max_chars 放进 file 对象，而实际是同级字段。
例如 task 1305 的第 4、15、18 次工具调用（从 1 开始）发生这种错误。
现有 schema 能表达约束，但说明和示例不足，通用 ContentLocation 的选项也较多。
一次 list_workspace 把根写作 `/`，而 WorkspacePath 要求相对路径 `.`。

正确形状是 `{"file":{"path":"manual.md"},"locator":{"char_start":20000},"max_chars":5000}`。
这说明先补清晰描述/示例值得验证，不足以证明必须扁平化或放宽接口。

### 3. Tool feedback 的纠错与完整性信号不足

`graph._error_message` 把原始 Pydantic/DuckDB 错误字符串装入 JSON 返回，没有统一
错误码、字段级修正建议或正确调用示例。task 1305 后面再次犯相同嵌套错误，说明仅仅
“模型看到了错误”并不代表它能稳定修正。部分 SQL 错误还返回很长的候选签名。

另一个已复现问题：`ReadFileTool.execute → _read_markdown` 默认先截到 20,000 字符，
随后才判断是否超过 max_chars，导致 manual.md 尚有后文时仍返回 `truncated=false`。
本轮实际调用确认 content 长度 20,000、char_end=20,000、truncated=false。
location 虽能表明读了哪一段，但没有清楚的 remaining/next cursor，容易误以为已读完。
这是工具反馈缺陷，不是模型凭空忽视证据。

### 4. Prompt / planning / termination 同样有问题

task 49 的 SQL 均成功：已经查出 BE 金额欺诈率约 12.2686%，NL 约 12.1815%，
最终却按欺诈笔数/绝对金额选了 NL；manual 定义 fraud 为欺诈金额占总金额比例。
这显示指标定义、文档证据与最终决策没有稳定对齐，不是 SQL 无法计算。

task 1273 后续单独查询已得到正确的含 null 结果 0.1201319444，最后仍选 true-only
的 0.117667，而 reference 为 0.120132。既有查询层误导，也有 wildcard 规则取舍问题，
二者的贡献不能凭一条轨迹拆成精确比例。两题还有不遵守“只输出答案”的格式问题。

task 1305 共 24 次工具调用只有 3 次显式错误，后期仍在变换筛选条件、搜索 wildcard，
还引入题目没有要求的 capture_delay 条件，最终没有收敛。因此 recursion 不等于 tool error
累计太多；有持续验证、任务约束漂移和缺乏明确停止判据。

当前 system prompt 只有原则性的“证据足够就停止、错误可恢复”。runtime 没有将剩余预算、
重复调用/无进展信号反馈给模型，也没有预算将尽时的收尾机制。`route_after_agent` 只检查
是否还有 tool_calls。用户看到的 `recursion limit` 是图的保护性终止，不是根因诊断。

配置 max_tool_rounds=12 实际只是设置 `recursion_limit=26`，并非严格限制 12 次工具调用。
这 7 个失败轨迹都有 13 条 AI 消息，每条可含多个工具调用。提高 limit 可能只延长循环、
放大 token 成本，不能当作主要修复。另一个诊断边界：`_arun` 目前也把最终答案提取失败
标成 GraphRecursionError，后续应分开；本次 7 条记录的错误文本确实是实际 limit=26。

## 下一步建议（尚未实施）

先修工具正确性：buffer-backed view 重复读取与截断/分页信号；用真实 SQL、重复扫描、
UNION/CTE/self-join 等确定性回归验证。工具返回可信后，再补参数示例和短小可操作的错误
反馈，观察重复错误率；然后单独测试基于证据/假设/预算的规划和收尾策略。
不要把 DABstep 答案或专用筛选条件硬编码进 runner/prompt。

保持相同任务和模型设置，分组改动、复跑并比较完成率/正确率、重复调用、工具错误、
token/延迟；若更换模型则另建 baseline。现在没有对照实验，不能断言某一层是唯一根因。
日志写入、磁盘容量和隐私也仍是本地开发级保障，不是生产审计系统。
