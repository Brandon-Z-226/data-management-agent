# v0 - 工具可靠性与运行边界

日期：2026-10-12 至 2026-10-15

## 版本目标

v0 已经跑通 User task → Agent → Tool → Workspace/Data → Final answer 的完整链路，
并建立了 benchmark 和运行日志。但真实模型 baseline 暴露出四类问题：查询结果可能不稳定，
文件读取的截断信号不可信，参数错误难以纠正，以及 Agent 会反复调用工具直至图递归上限。

这一轮 v0 修复的目标是让工具证据可信、错误可恢复、运行过程可控，并用真实评测明确
后续架构升级需要解决的能力瓶颈。它不改变单 Agent 的自由工具调用框架，不增加规划、
验证、上下文压缩或记忆，因此仍属于 v0，而不是新的 Agent 架构版本。

## 已完成的改进

### 数据查询与文件读取可靠性

结构化数据在查询前物化到本次调用独立的内存表，避免同一 JSON 数据被 UNION、子查询、
CTE 或自连接反复扫描时产生互相矛盾的结果。查询仍然只读，没有增加持久数据库或跨请求缓存。

文件读取重新明确了请求范围、实际返回范围和下一页位置。Markdown 不再把尚未读取的后文
误报成完整结果；CSV 和 JSON 数组按完整记录分页，不返回半行或被截断的 JSON。
字符预算不足以容纳一条完整记录时明确失败，不再返回无法继续的空结果。

这组修改解决了 v0 中已经复现的静默查询错误和错误截断。代价是结构化查询需要全量物化
输入，内存占用有所增加；大型文件优化和缓存仍未处理。

### Tool interface 与错误反馈

五个只读工具补充了模型可见的参数说明和通用示例，明确工作区相对路径、文件引用、
locator、字符预算、SQL 数据源和行数限制。检查文件和执行查询共用同一套数据加载规则，
CSV 空表头、列名和 SQL 类型现在保持一致。

Tool error 增加稳定的错误码、字段位置、简短原因、建议动作和合法参数示例。
参数错误、资源不存在、SQL 错误、数据错误和内部故障能够区分；完整异常和 traceback
只进入本地日志，不占用模型上下文。工具内部输出错误不再伪装成模型参数错误。

这些反馈能够帮助模型修正明确的参数错误。它仍然不能判断一个成功执行的 SQL 是否使用了
正确的业务指标；Tool success 只表示调用完成，不代表答案语义正确。

### 有边界的错误恢复与终止

运行过程增加工具轮次、调用次数和相同失败调用的上限。相同参数连续失败后不再原样执行；
内部故障采用更保守的阻断策略。触及边界后停止工具阶段，并进行一次不提供工具的收尾。

结果状态区分正常完成、受限收尾和运行失败。被边界阻止的调用保留在 trajectory 中，
但标记为未执行，不计入工具执行错误。缺少最终答案、模型请求失败、收尾失败和真正的
图递归上限也分别记录，不再统一误报成 recursion limit。

这一机制解决了无边界循环和错误分类问题，但只是止损策略，并没有自动提升规划或正确率。

## 验证情况

离线测试目前为 130 项，覆盖查询稳定性、完整记录分页、Tool schema 和结构化错误、
检查/查询元数据一致性、调用预算、重复失败阻断、受限收尾、日志、benchmark 和 UI。
真实 DABstep 数据上的重复查询与分页验证结果稳定。脚本化模型测试只证明控制流和接口行为，
不作为真实模型能力评测。

2026-10-14 使用 deepseek-flash 对 task 5、49、1305 进行了真实模型复测。

运行版本：`a2807b4d89224fae313ef1da7a4f126c29857e4a52962a83f2580812195b2e1d`。

仍然重复同一种指标错误，task 1305 也没有得到正确答案，不能宣称 Agent 能力已经改善。

## 当前主要问题

当前瓶颈已经从工具正确性转向语义理解、规划和收敛：

- 模型拿到明确业务定义后，仍可能用直觉覆盖文档证据。
- Agent 没有显式表示指标、分母、筛选条件、公式和待验证假设，成功 SQL 容易被误当成答案。
- 模型会围绕已经识别的歧义持续 profiling，而不是执行能够区分候选答案的决定性查询。
- 现有重复检测只识别完全相同的失败参数，无法识别不断改写 SQL 的语义性无进展。
- 工具历史会持续累积，输入上下文和 token 成本随轮次快速增长。
- 收尾没有独立的输出预算；模型即使被要求证据不足时停止，也可能继续长时间推理并猜测。
- 费用数据用空列表表达通用规则，而文档只明确说明 null，增加了 wildcard 判断难度。

这些问题部分来自 deepseek-flash 在当前轨迹中表现出的判断和指令遵循能力，部分来自 Agent
缺少规划、验证和阶段性约束。单纯增加工具轮次只会放大成本；单纯更换更强模型可能提高
结果，但不能替代通用的可靠性机制。

## 最终评测

2026-10-15 使用相同 deepseek-flash 和默认运行预算完成 10 个 dev tasks。
结果文件：`data/external/dabstep_benchmark/results/20261015T092603Z_deepseek-flash.jsonl`；
运行版本仍为 `a2807b4d89224fae313ef1da7a4f126c29857e4a52962a83f2580812195b2e1d`。

| 指标                            | 结果                        |
| ------------------------------- | --------------------------- |
| 正常完成 / 受限收尾 / 失败      | 5 / 4 / 1                   |
| 自动匹配正确                    | 1/9 个有答案任务，整体 1/10 |
| 正常完成率                      | 50.0%                       |
| 工具调用预算 / 工具轮次预算触限 | 3 / 1                       |
| 服务报告的 total tokens         | 1,316,086                   |
| 合计任务耗时                    | 553.150 秒                  |

这次评测确认修复后的 v0 能够完整记录工具调用和终止状态，复杂任务不再统一表现为图递归异常；
同时也确认工具可靠性和止损策略没有转化为答案正确率提升。自动 correctness 仍是严格的
规范化文本匹配，集合顺序和极小数值差异也可能被判为错误，因此它不是人工语义评分。

## 版本结论与后续方向

v0 的工具可靠性与运行边界修复到此定稿。它解决了初始 baseline 中的工具执行不稳定、
读取完整性、接口纠错和无边界循环问题，但保留了原有 `agent → tools → agent` 框架。
正常完成、受限结果和失败现在可以准确区分，Agent 仍然高度依赖模型自行理解任务、
维护上下文、规划查询、验证答案并决定何时停止。

Agent v1 需要进行认知编排层的结构升级，而不是继续增加工具或放宽运行预算：

1. 在数据查询前明确任务中的业务定义、目标指标、筛选条件、公式和必要证据。
2. 把文档定义作为查询口径的约束；存在多个合理解释时，用一个决定性查询比较候选口径。
3. 获得候选答案后进行证据校验，检查它是否真正回答原问题，而不是继续无目的探索。
4. 预算进入后段时停止发现性 profiling，只允许补齐缺失证据或完成最终计算。
5. 为普通模型响应和受限收尾设置独立输出预算；无法支持答案时明确失败，不输出猜测值。
6. 控制进入模型上下文的重复和低价值工具结果，降低长轨迹的 token 放大。

下一版本先复测相同三题：task 5 不能回退；task 49 必须依据 fraud rate 选择 BE；
task 1305 必须执行同时处理 account type 和 MCC wildcard 的计算并得到 0.123217。
随后再运行完整 10 题，与初始 v0 baseline 分别比较正确率、正常完成率、受限任务、
工具错误、token 和耗时。
