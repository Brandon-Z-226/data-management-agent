# v0 - 最小可运行基线与失败诊断

日期：2026-10-09

## 版本概述

v0 建立了第一个可运行的单轮数据 Agent：用户问题经过 LangGraph Agent，由模型自主选择
只读工具和参数，访问本地 Workspace 中的文档、CSV 和 JSON 数据，最终返回答案。

这一版本包括本地文件 Workspace、文件发现与读取、BM25 文档搜索、DuckDB 数据查询、
命令行入口、Streamlit 调试页面和 DABstep benchmark runner。运行过程能够保存问题、
模型消息、工具调用、结果、错误、耗时和 token usage，并用 conversation、thread、task、
turn 和 execution 标识区分不同运行。日志和评测数据仅保存在本地。

v0 的价值是证明完整工程链路能够运行，并建立可以复现和分析失败的基线；它还不是一个
可靠的数据分析 Agent。

## 真实模型 baseline

使用 deepseek-flash 顺序运行 10 个 DABstep dev tasks。结果保存在
`data/external/dabstep_benchmark/results/20261008T140653Z_deepseek-flash.jsonl`。
这次历史运行早于版本快照机制，因此没有精确源码指纹，不能事后补造。

| 指标 | 结果 |
| --- | --- |
| 输出最终答案 | 3/10 |
| 自动匹配正确 | 1/10 |
| 达到 recursion limit | 7/10 |
| 工具调用 / 显式错误 | 229 / 24 |
| 合计任务耗时 | 526.485 秒 |
| 服务报告的 total tokens | 2,141,703 |

task 5 正确；task 49 和 1273 输出了错误答案；其余 7 题没有最终答案。
10 题的小样本只能用于定位当前失败，不能代表完整 benchmark 水平。

## 主要问题

### 查询结果不可信

同一个 JSON 数据源在 UNION、多个子查询等场景中被反复扫描时，部分分支会偶发返回空结果。
相同查询曾得到互相矛盾的计数，但都被标记为 success。工具提供错误证据时，模型和 prompt
无法自行恢复，因此数据查询正确性是首要问题。

### 文件读取完整性不明确

长文档默认只返回前一部分，却可能标记为未截断；没有清楚的剩余范围和下一页位置。
模型容易把局部内容误认为完整文档。CSV 或 JSON 如果按字符直接截断，也可能无法安全续读。

### Tool interface 与错误反馈不够友好

模型经常把 locator 和字符预算放进错误的参数层级，或把根路径写成绝对路径。
原始校验错误缺少稳定错误码、字段级修正建议和正确调用示例，导致相同错误反复出现。
文件检查与 SQL 查询还可能报告不同的列名或类型。

### 业务语义和最终决策不稳定

task 49 已经计算出 BE 的欺诈率高于 NL，最后仍按欺诈笔数选择 NL；task 1273 在后续查询
得到包含通用规则的正确候选后，仍选择了不完整口径。Tool success 只能说明查询执行完成，
不能保证指标、筛选条件和最终答案符合文档定义。

### 规划与终止失控

复杂任务会不断变化筛选条件、重复读取或搜索，却没有显式的假设、缺失证据和停止标准。
运行时只依赖 LangGraph 的递归保护，没有工具预算、无进展检测或预算耗尽前的收尾机制。
提高 recursion limit 只会延长循环并放大 token 成本。

## 下一版本方向

v0 后续先修复查询和文件读取的确定性，再改善 Tool schema 与错误反馈，并增加明确的运行
边界。工具证据可信之后，Agent v1 再通过架构升级处理指标定义、动态规划、答案验证和
收敛策略。各阶段使用相同任务和模型设置复测，分别比较正确率、正常完成率、工具错误、
token 和耗时；不把离线测试或“不再报 recursion limit”当成模型能力提升。
